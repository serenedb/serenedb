# CI

- Workflows, `scripts/ci/`, CI images and fixtures change, and failed or flaky jobs rerun, only when the user asks. Runs: [pull-requests.md](pull-requests.md).
- A red unit is reproduced natively: `scripts/ci/test.py --build-dir <a local build of the job's config> --config <config> --test '<unit>'` runs it with CI's scheduler, servers and services ([testing.md](testing.md)). Only a failure that needs CI's image or network goes through `scripts/ci/run_shard.sh <config> <bundle digest or build dir> 1/1 <timing.json> --test '<unit>'`, which runs the same in the CI image.
- pre-commit lints every workflow with actionlint (`.github/actionlint.yaml` names the self-hosted runner labels); what a job runs is a script that runs the same locally, through `test.py` or `run_shard.sh`.

## Containers

- Every container, network and volume a CI job or a test runner starts carries the label `serenedb.owner=$SDB_DOCKER_OWNER` when that variable is set: `labels: *owner` in compose files, and a service that starts more through the docker socket gets `SDB_DOCKER_OWNER` in its environment. Each job removes its owner's leftovers before checkout and at its end; an unlabelled one outlives a cancelled job and keeps writing into the next job's workspace.

## What a run covers

- The PR's pre-commit job first checks the gitlinks (`scripts/check_submodule_pointers.py --reachable`): one its submodule's remote does not serve or that is on no version branch fails it, one at an open fork PR head gets a pending `pre-commit` status. It then fetches the DuckDB family submodules whose gitlink the PR moves, so the checks see their sources, runs the hooks as a commit of the PR's change would (on every file when the change touches the hooks or their configuration, and on main), and checks that every fork commit a gitlink moves over is formatted and that duckdb's `regen:` commit is current (`scripts/duckdb_family.sh check`). `serenedb | build & test` waits for that job and does not start when it failed.
- **Trigger Jobs** runs `serenedb | build & test` (`build-manual.yml`): `perf`, `dev` (with coverage), `asan` (address, leak, undefined), `tsan` and `msan` built and tested on amd64, `perf` and `dev` built on arm64. Each config's tests run in shards sized from the timing store, where a unit a config hasn't timed yet is estimated from the other configs' times and arm64 from amd64's, and a shard whose plan differs from the build job's fails instead of running. A config planned as one shard runs it in its build job, on that box's build, and its bundle stays on the box; more shards go to test jobs, which run, like the coverage job, only on runners labelled `lan`, next to the store, so no bundle crosses the internet to reach them. The trigger comment's **Flaky check runs** (1, which turns it off, by default) runs the tests the diff changes that many times in every config, the gtests and DuckDB C++ tests of a changed test source included, and any failing run makes the test FLAKY; `perf` also runs the changed `pg/` and `any/pg/` tests against PostgreSQL (`test.py --postgres changed`), all of them when the run covers everything. `scripts/ci/classify-changes.sh origin/main` prints which gated suites a diff opens, all of them for a change to the test harness, the CI image or the root build files, and `scripts/ci/ci.py select-suites` turns them into `test.py` arguments; `asan`, `tsan` and `msan` leave out the DuckDB suites and the iresearch tests a diff opens, until the nightlies show them stable under the sanitizers.
- Opt-in boxes of the trigger comment (inputs of `build-manual.yml`): **Dev only** builds and tests the amd64 `dev` config alone, with its coverage, and reports as `serenedb | dev only`, which is not the merge check: a branch still needs a full run before it lands; **Ignore diff, run everything** runs every suite, whatever the diff opens; **Bugfix check** runs the changed sqllogic, recovery, driver and DuckDB sqllogic tests on the merge base's build, where each must fail; compiled tests (gtest, DuckDB C++, re2) are built into that build without the change, so a diff with no other changed test fails the check; **sqlite corpus** runs `tests/sqllogic/any/pg/sqlite` (`test.py --corpus`), which nothing runs otherwise, not even a diff that changes it; **All architectures** also tests the arm64 `perf` and `dev` builds, on the suites the diff selects (coverage stays on amd64); **BigLake** adds the tests against the real catalog; **DuckDB sanitizers** and **iresearch sanitizers** let `asan`, `tsan` and `msan` run the DuckDB suites and the iresearch tests the diff opens, as `dev` does (run everything runs them whatever these boxes say).
- Every build configures and builds in a fresh directory, through ccache shared by the boxes, and only the test binaries of the suites its config runs (`sdb_config` in `scripts/ci/config.sh`), the benchmark binaries only in `perf` and `dev`; a config whose build inputs did not change since a finished build reuses that bundle (`scripts/ci/ci.py digest`) from its box or the store. Only a bundle other jobs fetch goes to the store, so a tests-only PR rebuilds a single-shard config, from ccache, unless its box still holds the bundle.
- `dev` measures the coverage of the change, in its build job when that runs its one shard, in the `coverage` job after its shards otherwise: the PR comment has the summary; `gh run download <id> -n coverage-dev-linux-amd64` (`results-dev-linux-amd64` when dev ran one shard) fetches `coverage.json` with every uncovered changed line, branch direction, function and MC/DC condition. MC/DC covers decisions of up to 8 conditions; a wider one reports only its branches (#1896).
- A change lands fully covered: after each run, every uncovered changed line, branch direction, function and MC/DC condition the `coverage dev (linux-amd64)` job lists gets a test that reaches it ([testing.md](testing.md)), or, when no input reaches it, the code goes. The job only reports, so the gap is closed in the same PR, never left for later. A partial report (`partial: profiles of N of M shards`) lacks the missing shards' hits: check those gaps locally ([testing.md](testing.md), "Running", coverage) before writing tests for them.
- The nightly run (`serenedb | nightly`, `jobs-schedule.yml`) starts on main every day at 03:00 UTC (04:00 CET) and runs every suite in every config with long fuzz and stress budgets, every `pg/` and `any/pg/` test against PostgreSQL in `perf`, macOS, teaches the timing store, then the release pipeline; when everything is green, a scheduled run (or a manual one with `PUBLISH`) replaces the draft release and pushes the images tagged with the version and `nightly`. A manual run's `CORPUS` input adds the sqlite corpus.

## A red run

- A PR's first comment is the CI report (it starts with `<!-- serenedb-ci-report -->`), which only the runs write: the latest run's report, with one line per config, the failures with their first lines, sanitizer report signatures and the coverage of the change, and the earlier runs folded below it with their verdicts. The trigger comment follows it, and only people and the trigger write it; the `spawn-build-bot` label replaces it with a fresh one. `gh run download <id> -n report` fetches `report.json` with every failure.
- A failed unit reran alone: FLAKY when a rerun passed, deterministic otherwise; the run stays red either way. A crash or a hang (STUCK, with every thread's stack) is critical.
- A unit that also failed on main or in another PR within a week says where (`also failed in main (asan, 2 run(s), ...)`).
- `gh run download <id> -n failure-<config>-<location>` (with `-<shard>` for a config tested in shards) fetches the failed units' logs, server logs, sanitizer reports and stacks; `gh run view <id> --log-failed` shows each shard's summary.
- A failure whose fix isn't simple is skipped in that config with an issue: a line in `scripts/ci/skips/<config>.txt` (unit glob, kind, reason with the issue), never a retry or a weaker test.

## The store

- The store holds the build bundles, results (and an index of the failures), timings and coverage profiles under `/store/`, and the shared ccache under `/ccache/`; only the CI and dev machines reach it. Bundles, coverage profiles and artifacts go after 3 days, and the oldest of them earlier while the store's disk has less than 200 GB free; results stay 120 days. Results and timings are Parquet, read and written with the release image's `serened shell` (`scripts/ci/ci.py`).
- Its address is the `SDB_STORE_HOST` secret, which every CI job gets as an environment variable; on a dev machine, export it yourself. Without it, a local run uses no store. An infrastructure address never goes into the repository: it is public.

## CI images

CI installs nothing at build or test time: toolchains, driver packages and fixtures come from images, and a missing dependency fails the runner instead of being installed or skipped.

1. Add the dependency where the image picks it up: a system package in `scripts/ci/build-ubuntu.Dockerfile`, a driver package in that driver's manifest under `tests/drivers/`, a Python test-data package in `scripts/ci/test-data-requirements.txt`, a service with baked-in content as its own Dockerfile under `tests/sqllogic/fixtures/<name>/` (listed in `scripts/ci/build_images.sh`). Pin versions.
2. Build it locally: `./build_images.sh` in `scripts/ci` builds every image the registry lacks for this machine, under the tag CI uses, so the runners pick it up.
3. Commit. Every image is tagged with a hash of its inputs: `scripts/ci/ci.py image` names the build image from the files its Dockerfile reads, `tests/sqllogic/fixtures/image_tag.sh` a fixture's from its Dockerfile. A run of `serenedb | build & test` or the nightly first builds and pushes the images the registry lacks, each architecture natively on a runner of its own, then joined under the image's tag; `serenedb | create infra` does the same by hand. No tag moves: outside a checkout, take a specific tag, or the one `ci.py image` prints on your branch.
