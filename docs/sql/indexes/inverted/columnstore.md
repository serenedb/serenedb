Search tables (`WITH (storage = 'search')`) and the `INCLUDE`d columns of an inverted index keep their values in a **columnstore**: every index segment carries a `.col` file with one compressed column per stored column. This page covers how those columns are laid out, which codecs are available, how to choose one, and how to inspect the result.

## Segments and row groups

A stored column is written in **row groups** of `row_group_size` rows (122,880 by default, see [row-group size](./maintenance.md#performance)). Each row group is compressed into one or more **segments**; a segment is the unit a scan decodes and a filter prunes with its zonemap.

A list or map column stores each distinct value of a row group once: a row keeps a code for its value, and only the distinct values' elements reach the element column. Columns whose values repeat, such as attribute maps shared by every record of the same resource, shrink by their repeat factor, and a scan hands each vector of such a column out as a dictionary over its distinct values, so an expression over the column can run once per distinct value. A row group whose lists are almost all distinct skips the dictionary and keeps one entry per row.

Unlike a transactional table, whose segments must fit a fixed 256 KiB block, a columnstore segment can be as long as its codec needs. The `.col` codecs use that freedom: they seal a segment after the vector whose estimated encoded size crosses 256 KiB, never rewinding to fit, so a long string only makes its segment longer.

## Codecs

A column's codec is either picked automatically (`auto`, the default: the candidates are measured on the column's own rows and the smallest result wins, segment by segment) or named explicitly. Numeric columns use the transactional codecs and, under `auto`, the columnstore's numeric codec (described below); text columns use the columnstore's own string codecs, which share one layout and differ in their *shape* (a dictionary of distinct values with row codes, or one entry per row) and their *leaf* (how the entry bytes are encoded):

| Codec | Types | Shape and leaf |
| :--- | :--- | :--- |
| `uncompressed` | any | values as-is |
| `bitpacking`, `rle`, `alp`, `alprd`, `roaring` | numeric / boolean | the transactional codecs, unchanged |
| `dict_fsst` | text | dictionary, sorted and front-coded (each entry keeps only what it does not share with its predecessor), FSST-encoded suffixes; NULL is a dictionary slot |
| `fsst` | text | one entry per row, front-coded against the previous row, FSST-encoded |
| `dict_lz4` | text | dictionary, lz4 over the dictionary bytes |
| `dict_zstd` | text | dictionary, zstd over the dictionary bytes |
| `lz4` | text | one entry per row, lz4 over the row bytes, for long text with few repeats |
| `dict_zxc` | text | dictionary, [zxc](https://github.com/hellobertrand/zxc) over the dictionary bytes |
| `zxc` | text | one entry per row, zxc over the row bytes |
| `zstd` | text | one entry per row, zstd over the row bytes; on a transactional table, duckdb's codec (zstd over each 2048-row vector, no level) |

The row codes of a dictionary are bitpacked, run-length coded when the column is sorted or clustered enough for that to be smaller, or stored with the [numeric codec](#numeric-columns) when that is smaller still; the choice is made per segment. Codes take only the numeric codec's leafless encodings, never its `lz4` or `zstd` leaves, because every scan, filter and sparse read of the column decodes the codes of the rows it touches, and a compressed codes frame decodes several times slower than bitpacked codes. A scan that reads whole vectors of a dictionary column decodes the segment's dictionary once and hands out **dictionary vectors**, so it pays only for each row's code. Both shapes store their entries in frames, and a sparse read, such as a point lookup, a `LIMIT` or the few rows a selective filter keeps, decodes only the frames it touches; with the `fsst` leaf (16 KiB frames) it decodes only the runs of 16 front-coded entries it touches. The `lz4`, `zstd` and `zxc` leaves use one of two frame layouts per segment. In the default layout the first 32 KiB of a segment's entries form its first frame, and every later frame (16 KiB of text, 32 KiB for `zstd`) is compressed with that first frame as its dictionary, so small frames keep the ratio of large ones; a read that needs a later frame decodes the first frame once and keeps it for the following reads of the segment. The other layout stores 64 KiB frames without a dictionary, for text that shares little between entries, such as random identifiers. When a segment is compacted, the `lz4` and `zstd` leaves can also use a dictionary trained for the whole column: before writing a text column, the compaction samples about 4 MiB of its distinct values from 32 places spread evenly over all the segments it merges, trains a 64 KiB dictionary from them and stores it once for the column in the new segment's `.col` file. Every frame of the column, the first one included, is then 16 KiB and compressed with that dictionary. A column with too little distinct text for a full sample keeps sampling the row groups as they are written and trains once it has enough. A point lookup then decodes only the frame it needs, since the dictionary is loaded once per column and kept in memory. Columns with little text keep the first-frame layout, and a refresh never trains a dictionary. A `dict_fsst` dictionary is sorted, so a comparison of the column with a constant (`=`, `<>`, `<`, `<=`, `>`, `>=`), an `IN` list, or an `AND` / `OR` of them is answered by a binary search over the dictionary without decoding it, and `IS NULL` / `IS NOT NULL` need no decoding on any dictionary codec. Any other filter on a dictionary column is evaluated once per distinct value; when earlier filters of the same scan leave fewer than a quarter of a vector's rows, as with a join's `IN` or Bloom filter after a selective condition on another column, only the distinct values those rows reference are evaluated, until they reach half of the segment's dictionary. The one-entry-per-row codecs answer filters by decoding the vector.

Under `auto`, a text column measures its candidates on the segment being written. A measurement takes the first segment of a row group, encodes it in both shapes with `lz4` to settle the shape, then measures every leaf in the shape that won. `fsst` and level-1 `lz4` are cheap and are encoded in full; every other leaf and level is priced instead. A price takes the frame table, lengths and codes from the segment's counts, and the compressed bytes from compressing, exactly as the encoder would, the segment's first frame (which the later frames use as their dictionary) and one frame from each of eight equal stretches of the segment. The leaf with the smallest size wins and is encoded; the segment itself is written with the smallest encoding measured, which can be a higher level of the same leaf than the one the column keeps, and the following segments use the winner's codec. During a refresh, `fsst` wins whenever it is at most 5% larger than the smallest, since it decodes a single value without decompressing a frame. A compaction keeps the smallest: its segments are large, and a scan reads a sorted `fsst` dictionary in row order, which jumps across the whole dictionary, while the other leaves keep the entries in the order the rows first use them. A column measures every row group until a measurement picks the same codec as the one before it; from then on it measures less often: two row groups later, then four, eight, and every 16th row group while that holds. A measurement that changes the codec returns the column to measuring every row group. Every segment is also checked against its codec: when its size per input byte moves more than 25% away from what the codec measured, that segment is measured again against every candidate and the column returns to measuring every row group, so a column whose values change partway through a row group changes codec where they change. A compaction measures `fsst`, `lz4` at levels 1, 4 and 6 (4 and 6 are lz4hc, which decodes as fast as level 1) and `zxc` at levels 1 and 3. It leaves `zstd` out: on text, `zstd` is 10-25% smaller than the `lz4` leaves but decodes about three times slower, and the decoded dictionaries of a large table do not all fit in the object cache, so scans, filters and point lookups of a compacted table would pay that on most reads. [Name `dict_zstd`](#choosing-a-codec) on the text columns that queries seldom read. Each column finds its own levels: its first measurement in an index segment prices every level of each leaf's ladder and keeps the lowest level within 2% of the smallest, and the rest of the column keeps the level found. The same measurement picks the frame layout of each `lz4`, `zstd` and `zxc` leaf: the dictionary layout stays unless 64 KiB frames without a dictionary are at least 3% smaller. A codec named on a column always uses the dictionary layout. When values repeat (at most half as many distinct values as rows), the dictionary shape wins unless the one-entry-per-row shape is at least 10% and at least 4 KiB smaller per segment: a dictionary gives dictionary vectors, once-per-value filters and in-band NULLs, which a small size edge does not pay for. A column of mostly distinct values takes whichever shape is smaller. When a row group's first segment comes out larger than the same rows stored as-is, the row group falls back to the transactional codecs.

A dictionary decoded in full is kept in the database's object cache the second time its segment decodes it, while the cache has room, so repeated scans and filters of a dictionary column do not decode it again. The cache holds an eighth of `memory_limit` (at least 256 MB) unless `SET GLOBAL sdb_object_cache_size = <bytes>` says otherwise (0 restores the automatic size); a dictionary that does not fit is decoded again by every scan that needs it whole.

Compaction is where the expensive codecs run. A segment written by a refresh measures only the leaves that decode fastest, `fsst` and `lz4` at levels 1 and 4, and trains no dictionary: level 4 (lz4hc) costs an ingest more CPU than level 1 but makes fresh text about a tenth smaller and decodes just as fast, and compaction re-encodes the fresh segments with the full set. The background compaction task (every `compaction_interval`, 1 second by default) merges segments of similar size as they accumulate, up to 10 segments and 5 GB per merge, so this happens without a `VACUUM`; a merge becomes visible with the table's next refresh (every `refresh_interval`, or `VACUUM (REFRESH_TABLE)` when the background refresh is off). A segment that nothing merges with, such as a table written by a single refresh, keeps the refresh codecs until the next merge or a `VACUUM (COMPACT_TABLE)`. A `zstd` frame decodes several times slower than an `fsst` or `lz4` one, which shows on point lookups and cold scans; zxc reads like `fsst` at levels 3 to 5 and trades read and write speed for size at 6 and 7.

## Numeric columns

Under `auto`, a numeric column (integers, decimals, floating point, dates and timestamps) chooses, row group by row group, between the transactional codecs and the columnstore's numeric codec. The numeric codec rewrites a row group with one transform. The bit-packed transforms store every block of 1024 values (or runs) in as many bits as the block needs, each block from its own smallest value; the others narrow the result to 1, 2, 4 or 8 bytes per value:

| Transform | Stores | Suits |
| :--- | :--- | :--- |
| raw | the values as they are | random values, such as identifiers and hashes |
| frame of reference | each value minus the row group's smallest | values within a narrow range |
| bit-packed frame of reference | each value minus the smallest of its block of 1024, in the bits the block's largest difference needs | integers that vary less within a block than across the row group, or by a width that is not a whole number of bytes |
| delta | each value minus the previous one, less the smallest such difference | sorted or clustered values, such as timestamps and row ids |
| run length | each run of equal values once, with its length | long runs of repeated values |
| bit-packed run length | each run's value and length, each bit-packed like the bit-packed frame of reference, per block of 1024 runs; offered only when runs average four rows or more, since expanding shorter runs reads slower than unpacking every value | runs of small integers, and the row codes of text dictionaries |
| dictionary | a code into the row group's sorted distinct values, which are stored once | few distinct wide values, such as repeated hashes |
| bit-packed dictionary | the same codes, bit-packed per block of 1024 values in the bits the block's codes need | few distinct wide values without long runs |

Before the transform, an integer row group whose values share a common factor is divided by it: the codec finds the greatest common divisor of the row group's values, stores it once in the segment and transforms the quotients, and a read multiplies them back. Timestamps and decimals often carry such a factor, because their type keeps more precision than the data has: a `TIMESTAMP` that holds whole seconds is a multiple of 1,000,000 microseconds, and a `DECIMAL(18, 3)` of whole amounts a multiple of 1,000, so dividing it out saves the bits that only ever hold zeros (about 20 bits per value on such timestamps). A filter compares its constant with each frame's range multiplied back, so it skips the same frames as without the factor.

The raw, frame-of-reference, delta and dictionary streams can also be byte-shuffled (the first byte of every value, then the second byte of every value, and so on), which groups bytes that change slowly. The transformed stream is cut into 16 KiB frames, each stored as it is or compressed with `lz4` or `zstd`. Each frame records the smallest and largest value of its rows, so a filter on an integer, decimal, date or timestamp column skips the frames whose range cannot match without decompressing them, and a point lookup or sparse read decompresses only the frames it touches. Bit-packed frames hold 16,384 values (one block of 1024 runs for the bit-packed run length) and are never compressed: a scan unpacks each block of 1024 values straight into its output, and a point lookup or sparse read unpacks only the blocks it touches (a run-length frame unpacks its runs once and serves every row they cover).

How much decoding work a smaller row group may cost depends on the write. A refresh measures the transformed frames stored as they are and compressed with `lz4`, prices the `lz4` result 5% above its size and keeps the cheaper: `lz4` decodes at memory speed, so it costs a scan almost nothing where it shrinks hashes and other values that repeat at a distance. A refresh leaves `zstd` out, since its frames decode several times slower and the next compaction rewrites the row group anyway. A compaction measures the transformed frames stored as they are, compressed with `lz4` and compressed with level-1 `zstd`, prices every `lz4` result 5% and every `zstd` result 15% above its size, and keeps the cheapest: `zstd` frames decode several times slower than bitpacking, so they win where they shrink a row group by more than about 13%, as on timestamps, hashes and timings. A point lookup or sparse read of a compressed frame keeps the decompressed frame in the database's object cache from the second time its row group is read that way, so repeated lookups, `LIMIT` queries and selective filters do not decompress it again; full scans never fill the cache with frames. Floating-point columns stay leafless: `alp` and `alprd` decode about as fast as bitpacking and usually compress floats better than a byte codec over their bits, so the numeric codec only takes a float row group whose values repeat. Like a text column, a numeric column measures every row group until its choice repeats, then two, four, eight and every 16th row group later, and returns to measuring every row group when a row group comes out more than 25% larger than its choice measured or when the transactional codecs become smaller. `pragma_storage_info` names the codec `Numeric`.

## Choosing a codec

Name the codec on the column with `USING COMPRESSION`, optionally with the codec's own level in parentheses, which pins that level instead of letting `auto` tune it:

A list, map or struct column whose values are all text takes the text codecs too, and the codec then compresses every string inside it, the keys and the values of a map alike. This suits attribute maps that queries return but seldom filter on: name `dict_zstd` on them to store them smaller, and leave the text columns that queries search or filter on to `auto`, whose codecs decode faster.

On an inverted index, an `INCLUDE`d column takes the same names, with the same optional level, through `included (compression = '...')`:

<SqlLogicTest id="sql/indexes/inverted/columnstore/example_002" />

An index on a search table has no columnstore of its own: its `INCLUDE`d columns are the table's, and a codec named there applies to the table's column, overriding the column's own `USING COMPRESSION` for the segments written while the index exists. Dropping the index hands the column back to its own declaration.

The global `force_compression` setting applies to search tables as it does to transactional ones: it wins over `auto` and loses to a codec named on the column. A codec that cannot encode the column's type, or a columnstore-only codec or a `compression_level` on a transactional or temporary table, is rejected at `CREATE TABLE` / `ALTER TABLE`.
