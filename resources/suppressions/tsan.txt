# False positive lock-order-inversion in the serenedb catalog store path.
#
# TSAN reports a cross-thread deadlock between DROP COLUMN's DataTable
# copy-construct (LIdx -> LMeta -> LM) and that same txn's commit (LM -> LIdx),
# triggered by `ALTER ... DROP COLUMN` / catalog Drop/ChangeTable
# (Catalog::DropTableColumn / DropType / ChangeTable). It cannot deadlock:
#   - All real DuckDB storage locks (DuckTransactionManager transaction_lock,
#     DataTable::append_lock, TableIndexList lock) live ONLY in the hidden
#     __sdb_store database. User tables use SereneDBTransactionManager (no-op
#     commit, owns no DataTable), so they take none of these locks.
#   - Every store mutation runs through CatalogStore::ExecuteEntries, which holds
#     absl::MutexLock{&_mutex} (server/catalog/store/store.cpp) around the whole
#     BEGIN..ALTER..COMMIT. Both reported lock-order edges execute SEQUENTIALLY
#     on one thread under _mutex, so the lock instances never form a cross-thread
#     cycle. TSAN's deadlock detector is instance-agnostic and unaware of the
#     outer _mutex, hence the false report.
# Caveat: only valid while __sdb_store is the sole writable DuckDB-native
# transaction manager. Re-check if another native-DuckDB writable txn manager
# is introduced.
deadlock:sdb::catalog::CatalogStore::ExecuteEntries
# The same pair, reached by a path that does not run through ExecuteEntries: the DataTable
# copy-construct of a column change against that transaction's own commit.
deadlock:duckdb::DataTable::DataTable

# Lock-order inversions across the catalog's locks. NOT proven harmless -- these are
# suppressed so the sanitizer legs report what is new, and the ordering itself is an open
# workstream. What is known so far:
#   - The cluster catalog WAL vs a database's transaction lock is a real deadlock: one
#     commit holds the database lock and waits for the WAL, another holds the WAL and
#     commits that database. Suppressed, NOT fixed: taking the WAL first instead only
#     moved the deadlock (a commit then held the WAL across duckdb's own commit, which
#     waits on other transactions, and CI wedged twice on it). The fix is to stop holding
#     the WAL across work that waits -- buffer a transaction's records and splice them
#     under a short lock.
#   - MetaTransaction::GetTransaction holds its own mutex across
#     DuckTransactionManager::StartTransaction, so a bind that resolves entries in two
#     attachments takes those locks in whatever order the statement names them. Upstream
#     code; the fix is to start the transaction outside that mutex and re-check the map
#     under it, which needs the double-start race handled and belongs upstream.
#   - The WAL also cycles with the catalog read locks (CatalogSet::Scan /
#     GetEntryDetailed) and the oid horizon. No hierarchy is documented for those yet.
# Re-check every entry below once a lock order is written down; each one may be hiding a
# reachable deadlock, not a false positive.
deadlock:duckdb::MetaTransaction::GetTransaction
deadlock:duckdb::DuckTransactionManager::StartTransaction
deadlock:sdb::catalog::ScopedCatalogWal
deadlock:sdb::catalog::WriteOidHorizon
deadlock:duckdb::CatalogSet::Scan
deadlock:duckdb::CatalogSet::GetEntryDetailed
