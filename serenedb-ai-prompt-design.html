Adding ai_prompt to SereneDB

A SQL scalar that sends text to an LLM and returns the reply — the text-generation sibling of the existing ai_embed.

repo serenedb branch gnusi/term-dict 2026-06 status: plan, pre-implementation

TL;DR. Add ai_prompt(text, model, secret_name) → VARCHAR. It reuses the same openai CREATE SECRET as ai_embed and calls an OpenAI-compatible Chat Completions endpoint (POST …/chat/completions), returning choices[0].message.content as plain text. Chat Completions beat the newer Responses API and the legacy Completions API because it's the one interface every provider implements — including Ollama, which our CI uses.

1What we're building

SereneDB already has ai_embed(text, model, secret_name) → FLOAT[], which calls an OpenAI-compatible /v1/embeddings endpoint configured through a DuckDB secret. Unlike flock (which makes you register a model first), the model name is passed inline as a string. ai_prompt is the text-generation sibling, built the same way: 

-- one-time: point a secret at any OpenAI-compatible provider
CREATE SECRET llm (
  TYPE openai,
  api_key 'sk-...',                  -- sent as: Authorization: Bearer sk-...
  base_url 'https://api.openai.com',  -- default; override per provider
  prompt_path '/v1/chat/completions'  -- default; override per provider
);

-- then call it from SQL like any scalar
SELECT ai_prompt('Summarize in one line: ' || abstract, 'gpt-5.5', 'llm')
FROM papers;

Returns plain text. A NULL input row yields a NULL output row. The new secret key prompt_path mirrors ai_embed's embeddings_path — the secret key matches the function name.

OpenAI exposes three generations of text API. Choosing one fixes ai_prompt's wire format.

Completions is frozen and needs hand-written per-model prompt templating. Responses is excellent for agentic, stateful, reasoning-heavy work — but its wire format differs and it's OpenAI-lineage-only (absent on Ollama, Azure, Gemini, Anthropic, …). Chat Completions is the portable middle ground, and what we target.

3Why Chat Completions

We surveyed 24 providers. The single-message → text shape ({model, messages:[{role:"user",content}]} → choices[0].message.content) is byte-identical across every provider with an OpenAI-compatible chat endpoint, so one code path reaches them all. base_url + prompt_path absorb path differences; api_key → Bearer covers auth everywhere except Azure-with-API-key — already a limitation of ai_embed, so we stay consistent.

What the control columns mean

Tools / function calling

Give the model callable functions (JSON-schema params); it replies "call f(args)" instead of prose. Powers agents and tool use.

Structured / JSON output

Constrain output to valid JSON, optionally matching a schema ("Structured Outputs" / "JSON mode"). Guarantees parseable results.

Batch

Submit a file of thousands of requests; processed offline (~24h) at roughly half price. For bulk, non-interactive jobs.

Fine-tune

Train a custom variant of a base model on your own data; get back a private model ID you call like any other.

None of these four are exposed by ai_prompt(text, model, secret) — it's a single-shot text→text call. Tools and Structured output could become future optional args; Batch and Fine-tune are control-plane operations that don't fit a scalar SQL function.

5One wire format per capability

Each AI capability has its own de-facto wire format and parser, independent of ai_prompt:

  • Chat → OpenAI Chat Completions — messages → choices[0].message.content. Near-universal. This is ai_prompt.
  • Embeddings → OpenAI /embeddings — input → data[].embedding. Already shipped as ai_embed.
  • Rerank → Cohere/Jina /rerank — {query, documents, top_n} → results[].relevance_score. A future ai_rerank targets this, not chat — detailed in §6. Offered by Cohere, Voyage, Jina, Together, vLLM, TEI, Pinecone, Bedrock.
  • Image-gen / STT / TTS / Moderation — each its own OpenAI-family endpoint and parser; each a possible future ai_* scalar.

6Spotlight — rerank & Qwen

Rerank is a separate wire format from chat. The de-facto standard is the Cohere/Jina shape, copied by Cohere, Jina, Voyage, Together, vLLM, HF TEI, Pinecone, Cloudflare and NVIDIA NIM: 

POST .../v1/rerank      Authorization: Bearer <key>
{ "model": "...", "query": "...", "documents": ["...","..."], "top_n": 5 }
→ { "results": [ { "index": 0, "relevance_score": 0.97 }, ... ] }

Crucially, cross-encoder / LLM rerankers score each (query, document) pair independently — the score is absolute relevance, not a relative ordering that needs the whole set. That makes rerank fit a row scalar (below).

Qwen rerankers

Qwen ships a strong open reranker line — Qwen3-Reranker (0.6B / 4B / 8B) and Qwen3-VL-Reranker (multimodal). They're instruction-aware, LLM-based rerankers that score from yes/no token logits. Two ways to reach them:

A · Self-host with vLLM — exposes the Cohere-compatible /v1/rerank above:

vllm serve Qwen/Qwen3-Reranker-8B --port 8888 \
  --hf_overrides '{"architectures":["Qwen3ForSequenceClassification"],
                   "classifier_from_token":["no","yes"],
                   "is_original_qwen3_reranker":true}'

The original model wants its chat template wrapped around the query/documents; the is_original_qwen3_reranker override applies it. Also servable via HF TEI / Infinity.

B · Alibaba DashScope (managed) — native shape, not OpenAI/Cohere-compatible, and the model families even differ:

ModelPathBody
qwen3-rerank…/compatible-mode/v1/reranksflat query + documents
qwen3-vl-rerank, gte-rerank-v2 (retiring)…/api/v1/services/rerank/text-rerank/text-rerankinput:{query,documents} + parameters:{top_n}

Both return output.results[].{index, relevance_score} — note the output. wrapper, unlike Cohere's top-level results.

How a future ai_rerank would look

Target the Cohere/Jina /v1/rerank shape (a new rerank_path secret key, default /v1/rerank) — one code path that reaches Cohere, Voyage, Jina, Together, TEI, Pinecone and self-hosted Qwen3-Reranker via vLLM, reusing the existing secret + provider plumbing. Because each score is independent, it fits a row scalar: 

SELECT id, body
FROM docs
ORDER BY ai_rerank('quarterly revenue drivers', body, 'qwen3-reranker', 'reranker') DESC
LIMIT 10;

Internally it batches all rows' documents into one /rerank call (shared query + document batch) and maps results[].index → relevance_score back to rows — the same batching ai_embed / ai_prompt already do; top_n falls out of ORDER BY … LIMIT. DashScope's native shape would be a separate adapter.

7Implementation plan

New files

  • …/embedding/prompt.{h,cpp} — the ai_prompt scalar (bind, execute, register), mirroring embedding.cpp.
  • …/embedding/common.{h,cpp} — shared helpers extracted from embedding.cpp so both functions reuse them: RegisterOpenAISecretType (now also accepts a prompt_path key), FoldConstArg, LoadProviderConfig, and a shared ProviderBindData.

Modified files

  • embedding/provider.{h,cpp} — add prompt_path to ProviderConfig; add PromptBatch dispatch.
  • embedding/provider_openai.{h,cpp} — default prompt_path = /v1/chat/completions; factor the HTTP POST into a shared helper (reused by embeddings); add ParseCompletion and PromptBatchOpenAI (one request per non-null row).
  • functions/CMakeLists.txt — add the two new .cpp files.
  • server/query/server_engine.cpp — call RegisterPromptFunctions(db) beside RegisterEmbeddingFunctions(db).
  • tests/sqllogic/run.sh — the Ollama harness also pulls a small chat model and exports OLLAMA_CHAT_MODEL (e.g. qwen2.5:0.5b).

Test

New tests/sqllogic/sdb/pg/simple/ai_prompt_ollama.test_slow (the _ollama. suffix auto-launches Ollama). Asserts behavior, not exact text: length(ai_prompt(...)) > 0, ai_prompt(NULL, …) IS NULL, plus error paths (unknown secret, NULL/non-constant model arg, unreachable URL). No code comments, no gtest — consistent with ai_embed.
