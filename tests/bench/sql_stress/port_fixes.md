# Port fixes

Every query under `ports/` differs from its corpus copy only by the fixes listed here.
`run_corpus.py` runs the port when one exists and the corpus copy otherwise.
Rows marked "engine gap workaround" replace a PostgreSQL feature serenedb lacks with a one-for-one equivalent;
the gap itself is listed under [Engine gaps](#engine-gaps).

## Runner fixes

- `run_corpus.py` `absolutize` rewrote every string literal that named an existing path, so `'..'`, `'.'` and `'*'`
  (glob over `data/`) became absolute paths inside queries (for example xocolatl 2022 dec07 compared directory names
  with `'/.../data/..'` and returned a wrong answer). It now rewrites a literal only when it names a file, or when it is
  a glob that contains `/` or `.` and matches a file.
- `DIALECTS` now includes `clickhouse` and `datafusion`, so the ClickHouse queries and the three DataFusion queries run by default
  (the `other` dialect, 339 files of SQL Server, Oracle, BigQuery, Snowflake and similar engines, is still not run).
- A port may carry its own setup, `ports/<project>/<query name>.setup.sql`, which replaces the setup files the prefix
  rule would pick, and data files under `ports/<project>/data/`, which `absolutize` searches after the corpus.
- serenedb defaults to `integer_division = on` (PostgreSQL: `int / int` truncates); DuckDB, MySQL and ClickHouse divide
  integers exactly. The runner now issues `SET integer_division = false` before the setup scripts of every query in
  those dialects (for example billwallis 2024 day 13 answered 1838 instead of 480 because every `% 1 = 0` test passed).

## DuckDB-dialect differences

serenedb follows PostgreSQL where the two dialects disagree. These differences made DuckDB (and SQLite or ClickHouse)
queries fail or answer differently; the ports translate them as listed in the table above. They are deliberate, not gaps.

| Behaviour | DuckDB | serenedb (PostgreSQL) | Ports |
|---|---|---|---|
| `string_split(s, '')`, `str_split`, `split`, `s.split('')` | splits into characters | `string_to_array(s, '')` semantics: the whole string; a `NULL` separator splits into characters | `''` → `NULL` (billwallis, DBatUTuebingen, sekuel, lukaswelsch, grahamwetzler, asql, flummi) |
| Top-level `generate_series(a, b)` in a SELECT list | a list | a set-returning function (one row per value) | `range(a, b + 1)` (grahamwetzler 2023 04, sekuel 2023 04) |
| `format(...)` | fmt-style `{}` placeholders | PostgreSQL `%s` placeholders | `printf` (billwallis 2024 11) |
| `int / int` | exact division since 0.8 | truncating (`integer_division = on`) | the runner sets `integer_division = false` for the duckdb, mysql and clickhouse dialects; queries written for DuckDB 0.6 set it back on |
| A lateral column alias (a SELECT-list alias used later in the same list) | allowed everywhere | allowed, except inside the arguments of a set-returning function (`unnest`, `generate_subscripts`): `Failed to bind column reference "row" [10.1]`; PostgreSQL has no lateral column aliases | the aliased expression written out (DBatUTuebingen 2022 days 8, 23, 24; billwallis 2024 days 03, 05, 07, 09, 17, 21) |
| Untyped `NULL` as a recursive CTE anchor column | takes the recursive term's type | PostgreSQL types it `text` and rejects a non-text recursive term; serenedb rejects it too, with `Unimplemented type for cast (INTEGER -> "NULL")` | `NULL::int` (grahamwetzler dbt 2022 day 07); the text case is the engine gap above |
| `json_extract(j, path)`, `j -> path` on a `json` value | JSONPath (`'$.a'`, `'$[0]'`) | PostgreSQL `->`: a key or an integer index (negative counts from the end); a JSONPath string is looked up as a key and gives `NULL` without an error. `json_extract` of a `varchar`, and `json_set`/`json_insert`/`json_remove` of a `json` value, still take JSONPath | key/index arguments (dmkskd 5 DuckDB shaders, BRonen brainfuck) |
| Decimal literals (`0.5`) | `DECIMAL` too | `DECIMAL(p,s)`; PostgreSQL's `numeric` is unconstrained, see the engine gap above | `::DOUBLE` / `CAST(... AS DOUBLE PRECISION)` where the source engine has floats (SQLite, ClickHouse) |
| `CAST(double AS INTEGER)` | rounds | rounds (PostgreSQL too); SQLite and ClickHouse truncate | `CAST(trunc(x) AS ...)` in the SQLite and ClickHouse ports |

Other behaviour the ClickHouse ports had to work around (none of it is a PostgreSQL feature): macro expansion is not
hygienic (a lambda parameter inside a macro body captures a caller's identifier of the same name), `CREATE MACRO`
rejects a body that calls a function not defined yet, a macro body cannot reference a column of the calling query,
a macro cannot call its parameter (no higher-order functions), and subqueries are not allowed inside lambda expressions
(`subqueries in lambda expressions are not supported`).
